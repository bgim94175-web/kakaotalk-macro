# 무단 사용 방지 — 차단 범위와 차단 불가 범위

키 없이 APK 만 분석하여 사용하는 행위를 차단하는 것이 목표입니다. 실제 범위를 그대로 정리합니다.

## 핵심 원리

> 클라이언트(앱) 내부의 검사는 **결국 패치될 수 있습니다.** 따라서 "검사를 추가하는" 방향으로는 대응이 불가합니다.
> 본 앱이 채택한 방향은 **서버 없이는 앱이 무의미해지도록 설계하는 것**입니다.

## 1단 — 설정 암호화 (핵심 방어) ⭐

앱을 실제로 동작하게 하는 모든 값 — **발송 메시지, 대상 방 목록, 트리거 규칙, 자동응답 문구, 봇 설정** —
은 평문으로 저장하지 않습니다. `config_key` 로 유도한 AES-256-GCM 키로 암호화하여 저장합니다.

`config_key` 는 **서버가 라이선스 검증 성공 응답에만** 포함하여 전달하는 값입니다.
서버 산출식: `HMAC-SHA256(CONFIG_SECRET, 라이선스키 + "|" + 기기ID)`

앱 내부 유도: `HKDF-SHA256(ikm=config_key, salt=기기ID, info="kakaoauto-cfg-v1", 32바이트)`

따라서 **라이선스 검증을 한 번도 통과하지 못한 기기는 자체적으로 저장한 설정조차 복호화할 수 없습니다.**
라이선스 검사 코드를 패치하여 통과 상태로 변경해도 `config_key` 가 없으므로 발송할 메시지가 존재하지 않습니다.
앱은 실행되지만 어떤 동작도 수행하지 않습니다. → **크랙의 실익이 없습니다**

`config_key` 자체는 평문 저장을 금지합니다. AndroidKeyStore(`kakaoauto_cfg`, AES/GCM, 하드웨어 백업)로
래핑하여 저장하므로 루팅되지 않은 기기에서는 파일을 복사해도 추출할 수 없습니다.

## 2단 — APK 서명 핀닝

앱이 자체 APK 의 서명 인증서 SHA-256 을 계산하여 매 요청에 `app_sig` 로 전송합니다.
서버는 허용목록(`app_signatures` 테이블 + `ALLOWED_APP_SIGS` 환경변수)과 대조하여 불일치 시 `bad_app_sig` 로 거부합니다.

APK 를 수정하면 원래 서명이 무효화되어 **재서명이 필수**이며, 재서명하면 SHA-256 이 변경됩니다.
→ 리패키징한 APK 는 서버에 접속할 수 없습니다.

### 현재 이 방어가 실제로 차단하는 범위 (의도된 트레이드오프)

현재 저장소는 **서명키(`android/keystore/app.jks`)를 의도적으로 커밋한 상태이며**,
`android/build.sh` 의 `KS_PASS` 기본값(`kakaomacro2026`)도 소스에 평문으로 포함되어 있습니다.
고정 키가 없으면 사용자가 앱을 삭제하지 않고 다음 버전을 덮어쓰기 설치할 수 없기 때문입니다.
**업데이트 설치 가능성 ↔ 서명 핀닝 강도**를 교환한 선택이며, 이 구성을 유지합니다.

따라서 현재 설정에서 2단이 유효한 범위는 정확히 다음과 같습니다.

| 대상 | 2단 차단 여부 | 사유 |
|---|:---:|---|
| **저장소 접근 권한이 없는 제3자** (APK 만 확보한 경우) | ⭕ | 원본 키가 없어 재서명이 필수이며, 재서명하면 SHA-256 이 변경되어 `bad_app_sig` |
| **저장소를 읽을 수 있는 사용자** (협업자 · 유출본 소지자) | ❌ | 커밋된 키 + 소스의 기본 비밀번호로 **정품과 동일한 서명**을 생성할 수 있습니다 |
| **저장소가 공개로 전환된 이후의 임의 사용자** | ❌ | 위와 동일합니다. 히스토리에 1회라도 포함된 키는 회수할 수 없습니다 |

> 정품과 동일한 서명으로 제작한 개조 APK 는 `app_sig` 가 허용목록 값과 **일치하므로** 서버가 통과시키며,
> `bad_sig` audit 도 기록되지 않습니다. 기기에도 정품 위에 덮어쓰기로 설치됩니다.
> 즉 **해당 사용자에게는 2단이 적용되지 않습니다.**

따라서 **저장소 Private 유지가 이 방어의 전제 조건입니다.** 협업자 추가 여부도 이 기준으로 판단하십시오.
공개로 전환하는 시점에 2단은 소멸한다고 간주해야 합니다.

- 비밀번호는 환경변수로 전달할 수 있습니다 — `build.sh` 는 `KS_PASS` 를 **우선 확인**하고, 없는 경우에만
  기본값으로 처리하며 빌드 로그에 경고를 크게 기록합니다. CI 는 GitHub Secret `KEYSTORE_B64` + `KS_PASS` 를 사용합니다.
- 이관 1단계와 같이 `ALLOWED_APP_SIGS` 가 비어 있는 기간에는 **2단이 비활성 상태입니다**
  (서버가 서명검사를 건너뜁니다). 이관이 완료되면 v2.0 hex 를 설정하여 재활성화하십시오 — `DEPLOY.md` 4-2.

### 방어를 강화하는 방법 — 키스토어를 저장소에서 분리

핀닝을 저장소 접근자에게도 유효하게 적용하려면 키를 저장소에서 분리하고 **GitHub Secret 으로만** 관리하면 됩니다.

1. `base64 -w0 android/keystore/app.jks` → 해당 값을 Secret `KEYSTORE_B64`, 비밀번호를 Secret `KS_PASS` 로 등록
2. **로컬 백업을 먼저 확보**합니다(암호 관리자 + 외장 디스크. 키와 `KS_PASS` 를 동일 항목에 보관)
3. `git rm --cached android/keystore/app.jks` → `.gitignore` 에 `android/keystore/*.jks` 추가
4. 히스토리에 남은 키 정리 또는 키 교체 여부 판단
   (교체하면 사용자 전원이 앱을 삭제하고 재설치해야 합니다 — `DEPLOY.md` 4장)

구체적인 명령과 검증 순서는 **`android/README.md` 3-2** 에 정리되어 있습니다.
대가는 저장소가 백업 역할을 더 이상 수행하지 않는다는 점입니다 — **키를 분실하면 전원 재설치**입니다.
따라서 이 경로를 선택하는 경우 백업은 담당자가 직접 책임져야 합니다.

> ⚠️ 또한 이 조치를 적용해도 **2단이 최종 방어선이 되지는 않습니다.**
> 키스토어는 언제든 유출될 수 있으며, 유출 시점에 핀닝은 무효화됩니다.
> **실질적인 방어선은 1단(설정 암호화)과 5단(온라인 필수)** 입니다. 2단은 보조 수단으로 취급하십시오.

### 검사 강도 (`APP_SIG_MODE`)

| 값 | 동작 | 적용 시점 |
|---|---|---|
| `off` | 검사하지 않음 | 디버깅용 |
| `lenient` | **기본값.** `app_sig` 를 전송한 경우 대조하여 불일치 시 거부. 미전송 시 통과 | 구버전(v1.8)과 공존하는 이관 기간 |
| `strict` | `app_sig` 필수 + 목록 일치 필수 | 전원 v2.0 전환 후 |

`lenient` 에 남는 취약점은 **`app_sig` 필드를 의도적으로 제외하여 전송하는** 크랙입니다. 이는 코드를 분석할 수 있는
사용자만 가능하며, 그 경우에도 1단(설정 암호화)으로 인해 앱은 사용 불가 상태입니다. `strict` 로 상향하면 해당 취약점도 차단됩니다 —
단 v1.8 사용자가 전원 차단되므로 `DEPLOY.md` 4-2 의 단계를 준수하십시오.

## 3단 — 변조 / 디버그 탐지

앱이 아래 항목을 검사하여 `tamper` 문자열로 서버에 보고합니다 (거부하지 않고 기록만 수행 — 오탐으로 정상 사용자를 차단하는 손실이 더 큽니다).

- `FLAG_DEBUGGABLE` (디버그 빌드)
- `Debug.isDebuggerConnected()` (디버거 연결)
- 설치 출처 이상 (`getInstallerPackageName`)
- 에뮬레이터 지표 (`Build.FINGERPRINT`, `MODEL`)
- APK 경로가 `/data/app` 외부

관리자앱 [기록] 탭에서 `tamper` 항목이 적색으로 표시되므로, 분석 시도를 확인할 수 있습니다.

## 4단 — 1키 1기기 + 세션 회전

- 최초 검증 성공 시 `device_id`(ANDROID_ID)가 키에 **영구 고정**됩니다. 다른 기기는 `device_mismatch` 로 무조건 거부됩니다.
- `device_fp`(하드웨어 지문: 제조사|모델|기기|보드|SDK|ABI 해시)가 변경되면 `takeover` 로 기록됩니다 — ANDROID_ID 복제 탐지용입니다.
- **동시 사용 차단**: `/verify` 성공 시마다 새 `session` 토큰이 발급되고 이전 토큰은 무효화됩니다.
  기존 기기의 heartbeat 는 `session_superseded` 를 수신하고 **즉시 전체 기능이 잠깁니다.**
  → ANDROID_ID 를 복제해도 두 기기가 동시에 정상 동작할 수 없습니다.
- 기기 교체는 **관리자 초기화만** 가능하며, 초기화 횟수(`reset_count`)가 누적 표시되므로 남용을 확인할 수 있습니다.

## 5단 — 온라인 필수 + 유예

- 최초 활성화는 온라인 상태에서만 가능합니다.
- 이후 기본 6시간(`recheck_ms`) 간격으로 heartbeat 를 수행합니다. 연속 실패가 3일(`grace_ms`)을 초과하면 전체 기능이 잠깁니다.
  (지하철·항공기 등 일시적 오프라인은 3일까지 허용됩니다)
- **시계 조작 방어**: 저장된 `last_ok` 보다 현재 시각이 과거인 경우 즉시 잠금 처리하고 재인증을 요구합니다.
  (기기 날짜를 과거로 변경하여 만료를 회피하는 방식을 차단)

## 6단 — 기능 게이트 단일화

모든 발송·봇 실행 경로는 `License.allowed(context, feature)` **단일 지점만** 통과합니다.
검사를 여러 위치에 분산하지 않습니다 — 우회 지점만 증가시킬 뿐입니다. 이 한 지점만 유지하면 전체가 보호됩니다.

## 차단하지 못하는 범위

| 공격 | 차단 여부 | 사유 |
|---|---|---|
| APK 디컴파일 후 코드 분석 | ❌ | 난독화를 적용하지 않았습니다. 차단하려면 R8/ProGuard 를 적용해야 하지만, 본 앱은 Gradle 없이 빌드하므로 현재 구조에서는 추가 작업이 필요합니다 |
| 라이선스 검사 코드 패치 | ⭕ 무의미 | 패치해도 `config_key` 가 없어 설정 복호화가 불가하며 → 발송할 메시지가 존재하지 않습니다 |
| APK 재서명 후 배포 | ⭕ | 서명 SHA-256 이 변경되어 서버가 거부합니다 |
| 키스토어 유출 상태에서의 재서명 | ❌ | 서명 핀닝이 무력화됩니다. 키스토어는 저장소에 커밋되어 있고 `build.sh` 의 기본 비밀번호도 소스에 포함되어 있으므로, **저장소 Private 유지가 이 방어의 전제 조건**입니다 (위 2단 한계) |
| 정품 키 구매자의 계정 공유 | ⭕ | 1키 1기기 + 세션 회전으로 동시 사용이 불가합니다. 교대로 사용하려면 매번 관리자 초기화를 요청해야 하며 횟수가 기록됩니다 |
| 루팅 기기에서 KeyStore 덤프 후 config_key 추출 | ❌ | 정품 키로 1회 활성화한 기기라면 가능합니다. 정품 사용자가 자신의 설정을 복사하는 경우이므로 실질 피해는 없습니다 |
| 에뮬레이터 대량 생성 | ⭕ | 키 1개당 기기 1대이므로 키를 추가 구매해야 합니다 |

## 추가 강화 방안

**Play Integrity API** — 구글이 기기·앱 정상성을 서버에 보증합니다. 리패키징·에뮬레이터·루팅을 높은 신뢰도로 탐지합니다.
단 **Google Play 스토어 배포가 전제 조건**입니다. 현재와 같이 APK 를 직접 배포하는 방식에서는 사용할 수 없습니다.

본 앱은 카카오톡 자동화이므로 Play 스토어 정책(타 앱 조작)에 저촉될 가능성이 높으며, 현실적으로는
**1단(설정 암호화) + 5단(온라인 필수)이 최종 방어선**입니다. 이 두 항목만으로도 실질적인 방어 수준은 충분합니다.
