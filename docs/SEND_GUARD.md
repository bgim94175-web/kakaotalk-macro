# 오발송 차단 — 설계와 금지 사항

손님이 의도하지 않은 대화방(학원 선생님과의 개인 대화)으로 매크로 메시지가 발송된
사고가 있었다. 이 문서는 그 원인과, 다시 일어나지 않게 하기 위해 지켜야 하는 규칙을 적는다.

## 1. 사고의 원인 — 방 이름 부분 일치

`KakaoListener.findSession` 의 2차 탐색이 이랬다.

```java
if (have.contains(want) || want.contains(have)) { ... }   // 길이 제한 없음
```

대상 대화방 이름이 `수학` 이면 `수학 선생님` 세션에 걸린다. 사람 이름은 다른 이름의
일부이기 쉬우므로, 짧은 이름을 대상으로 두면 언제든 개인 대화방으로 나갈 수 있었다.
사진 전송의 화면 매칭(`KakaoAccessibility.match` 의 `L_PART`)도 같은 구조였다.

### 지금의 규칙

| 비교 | 판정 |
| --- | --- |
| `공지방` ↔ `공지방` | 같은 방 |
| `공지방` ↔ `공지방(12)` | 같은 방 (꼬리가 인원수·장식뿐) |
| `⭐공지방⭐` ↔ `공지방` | 같은 방 (장식만 제거하면 동일) |
| `수학` ↔ `수학 선생님` | **다른 방** |
| `공지방` ↔ `공지방 2기` | **다른 방** |

- 텍스트: `KakaoListener.sameRoomLoose()`
- 화면: `KakaoAccessibility` 의 `letters()` 비교 (`L_PART`)

**금지:** 발송 대상을 결정할 때 `contains` 기반 이름 매칭을 쓰지 마라. 찾지 못하면
추측하지 말고 발송을 포기하고, 이름을 정확히 맞추라고 로그에 알린다.

## 2. SendGuard — 어디로 보내면 안 되는지

기존 발송 조건(방해금지 시간·쿨타임·새 메시지 최소 개수·계정 간 간격)은 전부 **언제**
보낼지만 봤다. `SendGuard` 는 **어디로** 보내면 안 되는지를 본다. 순서대로 본다.

1. **전체 정지** — 모든 기능의 모든 발송을 멈춘다.
2. **보호 대화방** — 어떤 설정·어떤 기능으로도 발송 금지. 다시 감지되어도 대상이 되지 않는다.
   이름 기준이라 계정이 여러 개여도 함께 막힌다.
3. **1:1 개인 대화방** — 그 방에 대해 손님이 직접 동의(`RoomCfg.allowOneToOne`)하지
   않으면 발송하지 않는다. 단체방으로 **확인되지 않은** 방도 막는다.

### 1:1 검사를 적용하는 기능

| 기능 | 1:1 검사 | 이유 |
| --- | --- | --- |
| 자동발송 (`MACRO`) | 적용 | 앱이 먼저 말을 건다 |
| 메시지 추적 (`TRIGGER`) | 적용 | 앱이 먼저 말을 건다 |
| 자동응답 (`AUTOREPLY`) | 면제 | 1:1 이 본래 목적 |
| 대화방 관리봇 (`ROOMBOT`) | 면제 | 지정된 방의 명령에 답한다 |
| 미니게임봇 (`MINIGAME`) | 면제 | 지정된 방의 명령에 답한다 |

전체 정지와 보호 대화방은 **모든 기능**에 적용된다.

### 저장 위치

전체 정지와 보호 목록만 **암호화하지 않은 Prefs** 에 둔다. 설정은 라이선스 설정키로
암호화돼 있어서 인증이 풀리면 읽히지 않는데, 그때 차단이 함께 풀리면 가장 필요한
순간에 장치가 없는 셈이다. 둘 다 "막는" 값이라 평문으로 둬도 손해가 없다.

**금지:** 이 두 값을 암호화 설정으로 옮기지 마라.

## 3. 차단 지점 — 발송 경로가 하나가 아니다

단일 차단 지점은 **존재하지 않는다.** 경로를 전수 조사하고 반증한 결과다.

| 경로 | 최종 발사 지점 | 차단 지점 |
| --- | --- | --- |
| 텍스트 (6개 기능 전부) | `KakaoListener` `pi.send` | `sendTo(…, kind)` 1차 + private `sendTo(…, Session)` 2차 |
| 사진 — 알림 답장 | `KakaoListener` 별도 `pi.send` | `sendImageTo` 공개·private 양쪽 |
| 사진 — 채팅방 첨부 | `KakaoAccessibility` 전송 버튼 탭 | `ImageSender.sendWithResult` 큐 진입 + `openIntentFor` + `doSendAttach` 의 대상 방 확인 |
| 사진 — 공유창 | `KakaoAccessibility` 전송 버튼 탭 | 같음 + 공유창 행 선택 시 확실한 일치만 허용 |

지켜야 하는 것:

- **실제로 도달하는 방을 기준으로 판정한다.** 요청한 `ref` 만 보면, 세션 탐색이 다른
  방을 골랐을 때 보호 목록이 그 방을 막지 못한다. private 판에서 `s.ref` 도 본다.
- **사진의 첨부·공유창 경로는 카카오톡 화면을 직접 조작하므로 텍스트 차단 지점을
  지나지 않는다.** 이 두 경로에서 '대화방 열기 인텐트를 내주지 않는 것'(`openIntentFor`)이
  유일한 사전 차단 지점이다.
- **채팅방 첨부는 방을 직접 열지 않는다.** 이미 열려 있는 화면을 조작하므로, 열린 방이
  대상 방임을 화면에서 확인하지 못하면 전송 버튼을 누르지 않는다(`roomSeenEver`).
- **공유창은 행을 누르는 즉시 사진이 간다.** 정확히 일치 · 공백/이모지만 다른 일치 ·
  말줄임 표시가 실제로 있는 잘린 행까지만 누른다. 앞부분만 같은 행은 중단한다.
- **계정 간 간격으로 미룬 발송도 쏘기 직전에 재검사**하며, 기능 구분(`kind`)을 그대로
  들고 간다 — 잃으면 자동응답·봇이 1:1 규칙에 잘못 걸린다.
- **차단되면 활동 로그에 사유를 남긴다**(같은 사유는 10분에 한 번). 조용히 삼키면
  손님은 왜 안 보내지는지 알 수 없다.

### 금지 사항

- `sendToDirect` 한 곳에 검사를 넣고 "다 막았다" 고 하지 마라. 사진은 그 체인을 지나지 않는다.
- 발송 함수의 문자열(저장값) 오버로드를 다시 만들지 마라. 호출자가 없는 그 두 개가
  각각 1:1 검사와 계정 간 간격을 건너뛰는 우회 경로였고, 그래서 제거했다.
- `Session.pending` / `Session.open` 을 클래스 밖으로 내보내지 마라. 답장 인텐트가
  나가면 차단 검사를 통째로 우회할 수 있다. `openIntentFor` 는 검사를 지난 뒤에만 내준다.
- 발송이 늘어나는 새 기능을 넣을 때는 `SendGuard` 의 기능 구분을 추가하고 호출부에서
  넘겨라. 넘기지 않으면 2차 방어선(전체 정지·보호)만 걸리고 1:1 검사는 빠진다.

## 4. 단체/1:1 판정

`KakaoListener.groupState(ctx, ref)` 가 `GROUP_YES` / `GROUP_NO` / `GROUP_UNKNOWN` 을 돌려준다.

- **살아있는 답장 통로(Session)를 먼저 본다.** 발송은 그 통로가 있어야만 가능하고, 통로는
  알림에서 생기면서 판정을 같이 싣는다. 즉 보낼 수 있는 상황이면 판정은 거의 항상 확정이다.
- 방 캐시만 있으면 `lastAt > 0` 일 때만 믿는다. 구버전 저장값은 단체여부 칸이 없어서 전부
  1:1 로 읽히는데, 그걸 믿으면 업데이트 직후 단체방 발송이 통째로 막힌다.

판정 자체는 애매할 때 **단체방 쪽으로 기운다**(`EXTRA_IS_GROUP_CONVERSATION` 이 false 라도
발신자가 2명 이상이면 단체방). 그래서 단체방이 1:1 로 잘못 판정될 위험은 낮다 — 단체방
이름이 유일한 발신자 이름과 정확히 같은 경우뿐이다.

## 초기화와 안전장치

대상 대화방 화면의 「초기화」는 세 가지다 — 감지 목록만 / 개별 설정 전체 / 방 목록 전체.

**어떤 초기화도 보호 대화방과 전체 정지를 해제하지 않는다.** 초기화 한 번으로 안전장치가
조용히 풀리면 발송하면 안 되는 대화방으로 다시 나간다. 확인창에도 "유지됩니다" 를 적는다.

그리고 **개별 설정을 지울 때 방별 '다음 발송 시각' 을 다시 배분해야 한다.** 그 값이 방별
설정 안에 들어 있어서, 그냥 지우면 모든 대상 방이 "발송할 때가 됐다" 가 되어 다음 알람에
한꺼번에 나간다 — 방이 20개면 20건이 동시에 올라가는 도배가 된다.

# 계정 간 발송 간격

듀얼 메신저로 계정을 2개 이상 돌릴 때, 두 계정이 같은 대화방에 들어가 있으면 같은 방
이름으로 양쪽이 동시에 발송해 메시지가 중복된다. 판매자 선택은 **건너뛰지 않고 둘 다
보내되 간격을 두기** 다.

## 금지 사항 — 메모리 타이머로 미루지 마라

예전 구현은 `Handler.postDelayed` 로 직접 미루고 호출자에게 `true` 를 돌려줬다.
그 한 줄에서 결함 10여 개가 나왔다.

| 미룸 방식 | 결과 |
| --- | --- |
| `Handler.postDelayed` | `SystemClock.uptimeMillis` 기준이라 기기가 깊은 잠에 들면 시간이 멈춘다 |
| WakeLock | 발송 루틴이 끝나면 풀린다 — 미뤈 발송을 지켜주지 않는다 |
| 프로세스 종료 | 메모리 큐이므로 **영구 손실**. 디스크에 남지 않는다 |
| 즉시 `true` 반환 | 발송 통계가 올라가고, 쿨타임이 밀리고, **사진이 글보다 먼저 나간다** |
| 미래 시각 선스탬프 | 경과가 음수가 되어 대기가 간격보다 길어지고, '방금 보낸 계정' 이 자기 미래 스탬프를 만나 검사를 건너뛴다 |

화면 꺼둔 전용 폰이 정상 운영 조건이라는 점이 핵심이다. 그 상태에서 60초는 몇 시간이
되거나 아예 사라졌다.

## 지금 구조

`KakaoListener.send(ctx, ref, text, kind)` 가 세 가지를 돌려준다.

| 결과 | 뜻 |
| --- | --- |
| `SEND_OK` | 보냈다 |
| `SEND_FAIL` | 못 보냈다 |
| `SEND_HELD` | **아직 안 보냈다.** 호출자가 다시 올 시점을 정한다 |

`SEND_HELD` 를 성공으로 처리해서는 안 된다. 기능별 처리는 이렇다.

| 기능 | 보류되면 | 이유 |
| --- | --- | --- |
| 자동발송 | 그 방의 다음 발송 시각을 간격이 끝나는 때로 당겨 **알람에 맡긴다** | 알람은 `RTC_WAKEUP` 이라 기기를 깨우고 프로세스가 죽어도 살아난다 |
| 메시지 추적 | 보내지 않는다 | '즉시 발송' 이 약속이라 1분 뒤의 발송은 의미가 없고, 두 계정이 같은 키워드에 두 번 반응하는 것이 문제다 |
| 대화방 관리봇 · 미니게임봇 | 보내지 않는다 | 같은 명령에 두 번 답하면 도배다. 한 계정이 답했으면 다른 계정은 조용히 있는다 |
| 자동응답 | 간격을 적용하지 않는다 | 1:1 은 계정마다 따로다. 같은 사람이 두 계정에 각각 말을 걸었으면 양쪽 다 답해야 한다 |
| 수동 즉시 발송 | 안내만 하고 그대로 보낸다 | 손님이 직접 누른 발송이다. 조용히 안 보내면 "눌렀는데 안 갔다" 가 된다 |

## 그 밖의 규칙

- **실제로 보낸 뒤에만 기록한다**(`stampAccountSend`). 미리 찍으면 실패한 발송이
  다른 계정을 괜히 기다리게 하고, 보낸 적 없는 계정이 스탬프 주인이 되어 검사를 건너뛴다.
- **사진 발송도 기록한다.** 사진만 보내는 경우(수동·「수동 전송만」)가 있고, 기록하지
  않으면 다른 계정이 바로 뒤이어 보내 동시 발송이 된다.
- **경과 시간은 음수가 될 수 없게 조인다.** 기기 시간을 되돌려도 대기가 간격보다 커지지 않는다.
- **키는 `gapKey`** — 괄호 꼬리만 떼어낸 표준형이다. `normRoom` 완전일치만 쓰면 같은 방인데
  한쪽에 인원수가 붙어 「공지방」/「공지방(12)」 로 들어올 때 **막으려던 중복이 그대로 나간다**.
  숫자를 그냥 떼면 「공지1」과 「공지2」가 같은 키가 되므로 여는 괄호가 있을 때만 떼어낸다.
- **판정과 발송은 방 이름 단위로 묶는다**(`gapLock`). '비었나' 확인과 '보내고 기록' 사이에
  다른 스레드가 끼어들면 둘 다 보낸다 — 예약 발송은 자기 스레드, 봇·추적·자동응답은 알림
  스레드에서 돌기 때문에 실제로 겹친다. 잠금 맵을 **비우지 마라**: 비우는 순간 같은 방에
  서로 다른 잠금 객체가 나가 상호 배제가 깨진다. 한도를 넘으면 공용 잠금을 쓴다.
- **실제로 도달한 계정으로 기록한다.** 계정 정보가 없는 구버전 저장값(`acc="0"`)은 계정을
  가로질러 통로를 찾으므로, 요청 계정으로 기록하면 실제로 보낸 계정이 자기 기록을 못 보고
  바로 뒤이어 또 보낸다.
- **기록 맵은 오래된 항목을 버린다.** 방 이름이 바뀌면 옛 키가 계속 남는다.
- **간격은 최소 쿨타임보다 짧아야 한다.** 길면 두 번째 계정의 발송이 계속 뒤로 밀린다.
  설정 화면이 이 상태를 경고한다.

## 남는 한계

- 판단 재료는 **대화방 이름**뿐이다. 알림에 고정된 방 번호가 없어서 "같은 방" 과
  "이름만 같은 다른 방" 을 구분할 수 없다. 이름만 같고 실제로는 다른 방이면 그 방도
  간격만큼 늦게 발송된다. 알람으로 다시 보내므로 **누락이 아니라 지연**이고,
  간격(기본 60초)이 쿨타임(20~40분)보다 훨씬 짧아 실질 손해는 작다. 설정 화면에 이 사실을 적었다.
- 같은 방에 같은 홍보 문구가 간격을 두고 **두 번** 올라간다. 판매자가 그렇게 선택했다.
  도배로 보이지 않게 하려면 계정별 기본 메시지를 다르게 설정하는 방법이 있다.

# 대화방 이름 변경

대상 대화방은 `계정 + 그때의 이름` 으로 저장된다(`RoomRef`). 이름이 바뀌면 새 알림은
새 이름으로 들어와 답장 통로가 새 키로 생기고, 저장된 옛 이름으로는 아무것도 찾지
못한다 → 매 주기 "대화방 연결이 없습니다" 로 실패한다.

**이름으로 자동 추적할 방법은 없다.** 알림에 고정된 방 번호가 없다. 추측으로 자동
교체하면 엉뚱한 방으로 발송되는 사고가 난다.

## 지금 하는 것

1. **조용히 실패하지 않게 한다.** 발송 대상인데 3일 넘게 감지가 없는 방이 있으면
   홈과 대상 대화방 화면에서 알린다. 이게 가장 중요하다 — 예전에는 활동 로그에만 묻혔다.
2. **후보를 제시하고 판매자가 확인한다.** 같은 계정에서 최근 새로 감지된 미선택 방을
   후보로 보여주고, 고르면 대상 목록·방별 설정·발송 주기·보호 지정을 함께 옮긴다.
   자동으로 바꾸지 않는다.
3. **고정 식별자 후보를 기록한다.** `ConversationShortcutInfo.getId()`(API 30+),
   알림 `tag`, 알림 `id` 를 세션에 담아 진단 기록에 찍는다. 아직 발송 판정에는 쓰지 않는다.

## 금지 사항

- 이름 매칭을 느슨하게 해서 이름 변경을 흡수하려 하지 마라. 그게 오발송 사고의 원인이었다
  (이 문서 앞부분 참고).
- 고정 식별자로 통로를 찾도록 바꾸기 전에 **실제 기기에서 확인하라** — 그 값이
  존재하는지, 이름을 바꿔도 유지되는지. 불안정한 값으로 통로를 찾으면 엉뚱한 방으로 간다.
  확인 방법: 대상 대화방에서 메시지를 1회 받고 진단 기록의 「대화방 식별자 후보」 를 적어둔 뒤,
  카카오톡에서 그 대화방 이름을 바꾸고 다시 메시지를 받아 같은 값인지 비교한다.

# 계정 감지 — 되는 방식과 안 되는 방식

계정 구분은 **안드로이드 사용자(UserHandle)** 로 한다 — `Accounts.keyOf(sbn)` 가
`sbn.getUser().hashCode()` 를 쓴다. 카카오톡 안의 로그인 정보는 보지 않는다.

그리고 알림·화면 처리 모두 패키지명이 `com.kakao.talk` 인 것만 받는다.

- `KakaoListener`: `if (!KAKAO.equals(sbn.getPackageName())) return;` — 다른 패키지의 알림은 첫 줄에서 버린다.
- `KakaoAccessibility`: `info.packageNames = new String[] { KAKAO }` — 다른 패키지의 화면은 이벤트 자체가 오지 않는다.

| 방식 | 감지 | 이유 |
| --- | --- | --- |
| 휴대폰 내장 듀얼 메신저(삼성) · 듀얼 앱(샤오미 등) | 된다 | 복제된 카카오톡이 **별도 안드로이드 사용자**로 돌고 패키지명은 그대로 `com.kakao.talk` 다 |
| 업무 프로필(Island · Shelter 등) | 된다 | 같은 원리 — 별도 사용자 + 진짜 패키지 |
| 「다중계정」 등 제3자 복제·가상화 앱 | **안 된다** | 카카오톡을 그 앱 **안에서** 돌리므로 알림이 그 앱 패키지로 올라오고, 안드로이드 사용자도 같다 |

제3자 복제 앱은 "감지만 안 되는" 수준이 아니다. **그 계정으로는 아무것도 못 한다.**

1. 알림이 패키지 필터에서 버려진다 → 답장 통로를 못 잡는다 → 글 발송 불가
2. 통과시켜도 `getUser()` 가 같아 두 계정이 하나로 뭉개진다 → 계정 구분·계정 간 간격이 무의미
3. 접근성이 그 앱 화면을 못 본다 → 사진 전송 불가

## 금지 사항

- 제3자 복제 앱을 지원하려고 **패키지 필터를 느슨하게 하지 마라.** 가상화된 카카오톡의
  알림은 답장 액션의 `PendingIntent` 가 컨테이너 앱 것이고, 방·발신자 파싱이 의존하는
  `MessagingStyle` 정보가 보존되는지도 보장되지 않는다. 필터만 풀면 "감지는 되는데
  발송은 안 되는" 상태가 되어 문의만 늘어난다.
- 손님에게 복제 앱을 권하지 마라. 카카오톡 계정 정보를 제3자 앱에 넣는 것이고,
  계정 정지 위험을 손님이 진다.
